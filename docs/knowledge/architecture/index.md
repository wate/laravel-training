アーキテクチャ参考資料
=========================

概要
-------------------------

このディレクトリは、Laravelアプリケーションの構成パターンと設計手法を比較するための学習用参考資料です。
プロジェクトの採用方針を決める文書ではありません。
このプロジェクトの基本はLaravel標準のMVCとし、必要になった処理だけServiceやActionへ分けます。

位置づけ
-------------------------

| 場所                           | 役割                                         |
| ------------------------------ | -------------------------------------------- |
| `docs/architecture.md`         | プロジェクト全体の採用方針。現時点では未作成 |
| `docs/knowledge/architecture/` | 比較と学習のための参考資料                   |

参考資料の内容をそのまま全体へ適用しません。
採用する場合は、対象機能を1つに絞って試します。

概念とディレクトリの違い
-------------------------

設計の概念は、ディレクトリ構成だけでは表現できません。
概念は責務、境界、依存方向を表し、ディレクトリはファイルの置き場所を決めるだけです。
フォルダ名を揃えても、責務や依存方向が守られなければ設計にはなりません。

構成を採用するかは、次のような観点で判断します。

- 守りたいルールを言葉にできるか
- 変更やテストがしやすくなるか
- チームが同じ意味で使えるか
- フレームワークの標準と衝突しないか
- 構成を維持するコストに見合うか

具体的なパターンと例は各ページで扱います。
このプロジェクトでは、ディレクトリ名を揃えることより、依存方向と変更のしやすさを優先します。

比較
-------------------------

アーキテクチャパターンは、コードの配置と依存方向を決めるものです。
設計手法は、業務のモデリングと責務の分け方を決めるものです。

### アーキテクチャパターン

| パターン                     | 概要                                | Laravelとの相性                           | このプロジェクトでの扱い |
| ---------------------------- | ----------------------------------- | ----------------------------------------- | ------------------------ |
| MVC                          | Controller、Model、View             | 標準。CRUDに向く                          | 基本                     |
| MVC+Service                  | Controllerから業務処理を分離        | 自然。段階的に導入できる                  | 必要時に採用             |
| ADR(Action-Domain-Responder) | Action、Domain、Responder           | invokable ControllerとServiceで表現できる | 参考                     |
| レイヤード                   | 表示、アプリ、ドメイン、インフラ    | 理解しやすい                              | 参考                     |
| ヘキサゴナル                 | ドメイン+Ports&Adapters             | Repositoryで表現できる                    | 参考                     |
| オニオン                     | ドメイン中心                        | Clean Architectureに近い                  | 参考                     |
| Clean Architecture           | Entity、UseCase、Adapter、Framework | 依存方向を強制できる                      | 参考。全体採用はしない   |
| バーティカルスライス         | 機能単位で縦に切る                  | 機能追加に強い                            | 機能増加時に検討         |
| モジュラーモノリス           | 機能ごとにモジュール分割            | 中規模以上向け                            | 機能増加時に検討         |

### 設計手法

| 設計手法                        | 概要                                     | Laravelとの相性    | このプロジェクトでの扱い |
| ------------------------------- | ---------------------------------------- | ------------------ | ------------------------ |
| [DDD(ドメイン駆動設計)](ddd.md) | 境界づけられたコンテキストと戦術パターン | 複雑なドメイン向け | 参考。全体採用はしない   |

設計手法はアーキテクチャパターンと組み合わせて使います。
DDDは層構成を決めるものではなく、業務のモデリング手法です。

選び方
-------------------------

### アーキテクチャの選び方

- 単純なCRUD: MVC
- Controllerが太くなった: MVC+Service
- 1操作の流れが複雑: ActionまたはUseCase
- 複数の入口から同じ処理を呼ぶ: ServiceまたはUseCase
- データソースを差し替える: Repository
- 読み書きの形が大きく違う: CQRSを検討
- 監査や履歴が中心: Event Sourcingを検討

### 設計手法の選び方

- 業務ルールが複雑で長期運用する: [DDD(ドメイン駆動設計)](ddd.md)を1機能で試す
- 業務の言葉とコードを揃えたい: ユビキタス言語とValue Objectから試す
- 単純なCRUD: DDDを無理に適用しない
